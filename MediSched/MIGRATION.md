# Firebase → Supabase legacy cutover plan

**Planning only. No production export/import, account migration or hosted change was performed.** Local fixtures demonstrate implementation; they do not establish that real accounts exist or have migrated. Keep booking closed until conflicts and ownership are reviewed. Never use the normal future-only booking RPC to import historical records.

1. **Inventory and backups.** Determine whether the original Firebase project contains real accounts/appointments. Export Auth identity metadata and Firestore collections/rules to controlled offline storage after explicit authorization. Record counts and checksums. Preserve the repaired-source backup inside MediSched. Leave Firebase production intact as the rollback source.
2. **Auth identity mapping.** Firebase UIDs are not Supabase UUIDs. Sessions, verification status and passwords do not automatically transfer. Prefer fresh signup/password setup and verified email codes. Decide any hash-import compatibility in a separate reviewed plan; never promise password migration. Build an audited mapping of exact `firebase_uid → supabase_auth_uuid` using identity evidence. Email matches alone are insufficient where addresses changed, collide or are unverified. Reconfirm email ownership in Supabase. Missing/deleted/ambiguous owners are quarantined for review.
3. **Profiles and catalogs.** Let the Auth trigger create profiles for new users. For mapped accounts, reviewed administrator tooling can reconcile profile names; browser clients must not bypass RLS. Match legacy doctor/type names to the stable seeded IDs, including duplicate/trailing-space names. Unknown choices require manual mapping rather than fabricated catalog entries.
4. **Times and status.** Check repaired `startMs/startAt`, original date/time strings and supporting evidence. Confirm Asia/Manila semantics; the original app recorded no timezone. Preserve minutes and exact one-hour boundaries, translating to `timestamptz`. Normalize cancelled/canceled to cancelled with documented cancellation timestamps. Do not invent unavailable cancellation dates without a recorded provenance decision. Original deleted cancellations cannot be restored from this archive. Started visits remain historical active rows with Past computed by time.
5. **Conflict review.** Detect half-open overlaps by mapped doctor across all users, not per owner. Canonicalize off-grid starts, unknown owners, invalid ages, missing required fields and inconsistent timezones before import. The SQL constraints will reject unresolved overlapping active records. Do not auto-delete duplicates or silently move visits; record administrator/patient decisions. Keep conflicted records in a separate restricted review export.
6. **Separate historical import.** Prepare dedicated administrator-only import tooling after the mapping/reconciliation review. It must not be exposed as a public RPC or require broad client grants. Preserve original document IDs in an admin-only audit mapping to new UUIDs, retain timestamps/status/history and record provenance. Existing request UUIDs may only be retained if validated and unique. For cancelled records, set cancellation history consistently. Precompute/reconcile all active intervals before loading; the exclusion constraint remains enabled. Dry-run in a disposable project, then compare owner/count/status/time totals and every conflict decision.
7. **Verify staging.** Run actual Supabase signup/email codes/OTP, confirmed/unconfirmed sessions, RLS and direct-write rejection, two-user concurrent booking, midnight/adjacent boundaries, same-ID retries, cancellation retention/rebooking, saved booking when the Brevo notification fails, authenticated notification ownership and durable duplicate protection and logout. Confirm `btree_gist`, grants/function ACLs and empty search paths. Verify Auth and RLS through Supabase services, not only synthetic PostgreSQL Auth fixtures. Review privileged administrators/IAM and clinical retention/erasure rules.
8. **Authorized cutover.** Freeze old booking writes, capture a final delta and reconcile it while both systems' booking gates remain closed. Apply only a separately approved production plan to a dedicated MediSched project. Configure public client keys and redirects, review real email delivery and validate production reads with authorized test accounts. Enable `booking_configuration.enabled` and `migration_approved` only after signing off counts, ownership and all active intervals. Existing users must authenticate to Supabase; no Firebase session flag may grant access.
9. **Rollback.** Retain immutable exports and mapping logs. Before reopening Firebase, reconcile any new Supabase bookings/cancellations so rollback cannot double book or lose history. Freeze writes if verification fails; restore the previous frontend/config from the structured backup only through a reviewed process. Do not run both booking systems independently. Document user communication and rescheduling decisions.

Neither ZolTrack nor ZolNutrition's Supabase projects are part of this migration. This repository includes no automatic production import or cutover command. Hosted changes and real email require separate authorization.
